# Homelab Showcase Site — Build Runbook

**Target executor:** OpenCode (customised) driving Qwen3.8-27B via NInfer, subagents capped at 4
**Deploy target:** GitHub Pages
**Constraint:** animated data flows are *scripted and synthetic*. No live telemetry, no API calls, no backend.

---

## 1. What this is

A single-page, static, interactive diagram of the stack. The hero is the topology itself — not a headline over a screenshot. Visitors watch named scenarios play out as animated packets travelling between real components, and can click any node to read what it actually does.

**Audience:** security and platform engineers, and hiring managers who will judge engineering taste from this page.
**Primary job:** make the architecture legible in 30 seconds, and make the judgement calls visible in 3 minutes.

Non-goals: a dashboard, a blog, a live status page.

---

## 2. Assumptions to confirm before you start

If any of these are wrong, fix them here rather than mid-build.

- GitHub Pages, deployed from Actions. Public repo, so the source is part of the showcase — treat commit history and README as visible artefacts.
- Decide the repo name now, because it sets Vite's `base`. A project repo serves from `/<repo-name>/`; a `<username>.github.io` repo serves from `/`. Getting this wrong is the single most common Pages failure and it presents as a blank page with 404s on every asset.
- Desktop-first, but must not be broken on mobile.
- No analytics, no cookie banner.
- Diagram assets generated by ComfyUI are decorative only — the topology is real SVG, not a rendered image.

## 4. Scenarios — the animated flows

Five named sequences. Each is data, not code: an ordered list of hops with durations. The scenario engine reads them; adding a sixth should require no new code.

`src/data/scenarios.json`:

1. **Morning briefing** — the 08:30 job hands the day's threat intel to Claude Cowork, writes the returned briefing to local files, n8n's internal cron picks them up at 08:45, renders HTML, hands to Resend, lands in the work inbox. This is the only scenario where a packet crosses out of the house and back, and it should read that way.
2. **Task from Discord** — message arrives → Hermes → workspace as MCP sender → OpenCode → four subagents fan out → Mnemosyne read and write → Langfuse trace → result returns to Discord.
3. **Model swap** — a task needs imagery. llama-swap unloads Qwen, loads the diffusion model, ComfyUI generates, then the group returns to Qwen. This is the scenario that earns the page its keep: it shows the constraint being enforced rather than described.
4. **Health sweep** — cron fires checks across hosts, metrics land in Grafana.
5. **Off-network access** — a phone joins the tailnet and reaches Hermes with nothing exposed publicly.

Each scenario carries a short caption that appears while it plays. Write the captions as plain statements of what is happening, not marketing.

## 5. Tech choices

| Concern | Choice | Why |
|---|---|---|
| Build | Vite + TypeScript | Fast, boring, well represented in training data |
| Framework | **None** — direct SVG DOM | React re-render semantics and imperative animation fight each other, and a 27B model resolves that badly. Plain DOM keeps every phase independently testable |
| Animation | Web Animations API + CSS `offset-path` / `offset-distance` | Native, no dependency, GPU-composited, deterministic. Packets follow the same SVG path the edge is drawn from |
| Layout | Hand-authored zone boxes, edges routed as cubic Béziers between anchor points | Avoids pulling in a graph layout engine for a 21-node fixed diagram |
| State | One module exporting a small store with subscribe/notify | No library needed |

Explicitly rejected: React Flow, D3 force layout, GSAP, Framer Motion. All add surface area the model will misuse, and none earn their place at this size.

## 6. Design direction

The flows are the design. Everything static should recede so that motion is the only thing competing for attention.

**Palette** — colour is functional here. Each flow kind gets one hue, and those hues appear nowhere else on the page.

```
--substrate   #121A22   deep blue-slate canvas
--surface     #1B2530   zone fills
--rule        #34424F   idle edges, zone borders
--ink         #E4EAF0   primary text
--ink-muted   #8FA0B0   secondary text

--flow-control  #F2C14E   orchestration, task routing
--flow-memory   #7FB2A8   Mnemosyne reads and writes
--flow-infer    #A88BD8   GPU work
--flow-health   #6E9BD8   telemetry and checks
--flow-egress   #D96C7A   mail leaving the house
```

Idle edges sit at `--rule`. An edge only takes its flow colour while a packet is traversing it, then fades back over ~600ms. That means a still screenshot is nearly monochrome and the page only comes alive in motion, which is the point.

**Type** — Fraunces for the display line (variable serif, optical sizing, has actual character), IBM Plex Sans for body and UI, IBM Plex Mono *only* for literal machine strings: model names, `170 tok/s`, `NVFP4`, file paths. Mono is doing semantic work, not decorating labels.

Type scale from a 1.25 ratio. Body at 16px, line length under 70 characters in the inspector panel.

**Layout**

```
┌──────────────────────────────────────────────────┐
│  Fraunces display line, two lines max            │
│  one sentence of standfirst                      │
├──────────────────────────────────────────────────┤
│                                                  │
│         [ full-bleed topology canvas ]           │
│      zones as soft-bordered regions              │
│      nodes as small labelled anchors             │
│                                                  │
├──────────────────────────────────────────────────┤
│  ▸ Morning briefing  ▸ Task from Discord  ▸ ...  │
│  caption line for the running scenario           │
└──────────────────────────────────────────────────┘
                    ↑ node click opens right-hand
                      inspector panel, canvas dims
```

Left-aligned throughout. No centred text except the scenario caption.

**Restraint** — one bold move only: the packets themselves, which should have a genuine glow and easing that feels physical. Everything else stays quiet. No card grid, no section entrance animations, no hover lift on nodes (use a border-weight change instead).

## 7. Git model

Decide this before you type a command, because retrofitting it is painful.

- **`main` is deployable.** Every push to `main` triggers the Pages workflow. Nothing lands on `main` that has not passed its phase acceptance.
- **One branch per phase**, named `phase-N-slug`. Merge with `--no-ff` so the phase boundary survives in history — this repo is public and the history is part of what you are showing.
- **OpenSpec changes are proposed on `main`**, then applied on the phase branch. The proposal exists before the branch does, so the spec is reviewable independently of the code.
- **Conventional commits.** `feat:`, `fix:`, `chore:`, `docs:`, `spec:` for OpenSpec artefacts. Not because a tool consumes them, but because a reviewer reads them.
- **Commit at every acceptance checkpoint**, not at the end of a phase. If Qwen goes wrong on step 5, you want to reset to step 4, not to yesterday.
- **Tag each phase merge** `phase-N`. Cheap, and it gives you `git diff phase-3 phase-4` as a way to review what a phase actually changed.

Never commit: `node_modules`, `dist`, `.env`, editor directories, or anything containing a LAN address or tailnet hostname.

### Step 3 — Lock the data decisions and initialise OpenSpec

All three decisions below are settled — 3.1, 3.2 and 3.3 are recorded here as resolved. What remains is execution: write them down, initialise OpenSpec, commit. Do not skip the writing-down; on a public repo the reasoning is part of what you are showing, and future-you will not reconstruct it.

This step commits directly to `main` rather than a branch. It touches only docs and config — nothing that reaches `dist` — so the deploy is unaffected, and OpenSpec proposals need to live on `main` anyway.

#### 3.1 — Digest job placement *(resolved)*

The 08:30 job calls Claude Cowork, so the inference is off-box and llama-swap has nothing to do with it. The job runs on the workstation, so `digest` sits in `wsl` and `cowork` sits in `ext`.

This is transitional — the digest is being ported to local inference. Two consequences:

- **Say so on the site.** The `cowork` node carries `"transitional": true`, and the renderer should mark those nodes visibly: a dashed border, and the inspector copy stating it is being migrated. A hosted call on a local-infrastructure showcase is something an engineer spots in seconds. Labelled as in-progress it reads as an accurate snapshot; unlabelled it reads as an inconsistency you did not notice.
- **Make the flip cheap.** When the port lands, the change is `cowork`'s zone moving to `wsl`, the `digest-cowork` edge becoming a `digest-swap` edge, and the `transitional` flag coming off. No code. That is the return on putting topology in JSON rather than in components, and it is worth verifying at Step 5 by making the change locally and confirming nothing but data moved.

#### 3.2 — One-way edges *(resolved)*

Confirmed: fifteen edges are request/response and carry `bidirectional: true`. Six are one-way and correctly lack it:

```
opencode-langfuse   traces out, nothing back
cron-grafana        metrics out, nothing back
cron-n8n            trigger out, nothing back
digest-n8n          files out, nothing back
n8n-resend          message out, nothing back
resend-inbox        mail out, nothing back
```

Both categories are settled, so no flags change. Re-check only if you add a scenario later — nothing downstream catches a wrong arrowhead, because it renders perfectly and is simply untrue.

#### 3.3 — Direction model *(resolved)*

Accepted. Two flags, two concerns — `bidirectional` on the edge is a rendering fact, `reverse` on the hop is an animation fact:

```ts
type Edge = {
  id: string
  from: string
  to: string
  kind: FlowKind
  bidirectional?: boolean   // rendering: arrowheads both ends, or none
}

type Hop = {
  edge: string              // edge id, not a node pair
  at: number                // ms from scenario start
  duration: number
  reverse?: boolean         // animation: offset-distance 100% → 0%
}
```

Rejected: a second edge per return leg. It would take the edge list from 21 to roughly 36 and put two paths between most node pairs — either drawn, which is noise on a diagram whose job is legibility, or hidden, at which point the data stops matching the picture.

This matters at Step 7, where an awkward case will make "just add a second edge here" feel reasonable. It is not: a mixed model where some links are one edge and some are two is worse than either choice made consistently. If Step 7 genuinely cannot be expressed with these two flags, that is a signal to revisit this decision deliberately and change it everywhere — not to make an exception.

#### 3.4 — Write DECISIONS.md

At the repo root, alongside `README.md` — not in `docs/` or `openspec/`. It is read by humans browsing the repo, and root-level files are what people actually open. `openspec/` holds specs about what the code should do; this holds why the data is shaped the way it is.

Three entries, three lines each. Format matters less than the "why" being present:

```markdown
# Decisions

## Digest job runs on the workstation and currently calls Claude Cowork
Transitional — being ported to local inference. Not gated by llama-swap while it is hosted.
Consequence: `cowork` is an external node flagged `transitional`; scenario 1 is the only
flow that leaves the house, and it stops being so once the port lands.

## Edges carry `bidirectional`, hops carry `reverse`
Rendering and animation are separate concerns. One path per link, arrowheads from the
edge flag, direction of travel from the hop flag.
Rejected: declaring a second edge per return leg — doubles the edge list for no gain.

## Six edges are one-way, the rest are request/response
opencode-langfuse, cron-grafana, cron-n8n, digest-n8n, n8n-resend, resend-inbox.
Telemetry and mail only travel outward; everything else is a conversation.
Consequence: these six render with a single arrowhead, and the loader throws if a hop
sets `reverse` on any of them.
```

That last consequence is worth encoding as a validator rule at Step 4 — a hop setting `reverse` on a one-way edge should throw.

#### 3.5 — Initialise OpenSpec

```bash
openspec init
```

Then write `openspec/config.yaml`. Every proposal from Step 4 onward inherits these constraints, so you are not restating them in each one:

```yaml
schema: spec-driven
context: |
  Static single-page site, no backend, no framework.
  Build: Vite + TypeScript. Rendering: direct SVG DOM manipulation.
  Animation: Web Animations API and CSS offset-path only.
  Deploy: GitHub Pages via Actions, base path is not root.
  All topology and scenario content lives in JSON, never in code.
  All colour via CSS custom properties.
rules:
  proposal:
    - State which runbook step this implements
    - State what a reviewer should be able to see working afterwards
  specs:
    - Use Given/When/Then scenarios
    - Every animation requirement must state its reduced-motion behaviour
  design:
    - Name any new dependency explicitly and justify it, or state that none is added
    - Note determinism: no Math.random() in animation paths
  tasks:
    - Keep tasks small enough to complete without clearing context
    - Last task is always the step checkpoint from the runbook
```

The `rules` entries are what stop a proposal drifting. Without the dependency rule, Qwen will reach for an animation library at Step 7 and justify it in the design doc rather than in a conversation with you.

- `src/data/topology.json` and `src/data/scenarios.json` from sections 3 and 4

- `"prebuild": "npm run validate"`

**Checkpoint:** break an edge reference deliberately. `npm run validate` exits non-zero and names the bad id; `npm run build` refuses to run. Restore, commit, merge, tag `phase-1`, archive the change:

## 9. The OpenSpec loop

Four of the twelve steps are OpenSpec changes: **4** (data model), **7** (packet primitive), **8** (scenario engine), **10** (interaction), plus **11** (quality floor). The rest are ordinary work, deliberately — running a proposal cycle on a scaffold or a token application teaches you the overhead without the benefit, and that is how the process starts to feel like ceremony.

The documented flow is proposal → specs → design → tasks → implement. The operational path is `openspec init`, then `/opsx:propose`, `/opsx:apply`, `/opsx:archive`. A propose call creates `openspec/changes/<name>/` containing proposal.md, specs/, design.md and tasks.md.

**Where git and OpenSpec interlock:** propose on `main` and commit the artefacts there, so the spec is reviewable before the branch exists. Apply on the phase branch. Merge. Archive on `main` after the merge, so the consolidated spec only ever reflects code that shipped.

`/opsx:continue` picks up an in-flight change without re-reading everything, which matters because you are clearing context between steps.

### Config

`openspec/config.yaml` is written at Step 3.5, where the block appears in full. It carries the project constraints and the per-artifact rules, so proposals inherit them.

### Deltas, not rewrites

A delta is the change itself rather than the whole spec rewritten. When Step 10 adds the inspector, the delta describes the inspector — it does not restate how nodes render. A proposal that comes back restating existing behaviour is the signal to reject and re-propose narrower.

### Model discipline

Pin the preset for the whole build. A mid-step swap pollutes your Langfuse traces and makes a slow step read as a slow model when it was llama-swap doing its job.

Qwen at 27B has two habits to catch at the `tasks.md` stage, where they are cheap: reintroducing React idioms into vanilla DOM code, and hardcoding coordinates when layout maths gets fiddly.

## 10. Known risks

| Risk | Mitigation |
|---|---|
| `offset-path` with a raw `d` string has Safari quirks | Test Safari at Step 7, not Step 12. Fallback is animating `cx`/`cy` along sampled path points |
| Diagram becomes unreadable at 21 nodes | If crowding appears at Step 5, cut `openspec` as a visible node and fold it into the workstation zone caption. Do not cut `cron`, `pihole` or `langfuse` — each carries a scenario |
| Scenario timings feel arbitrary | Give each hop a duration proportional to what it represents — a Mnemosyne write is fast, a model swap is slow. The timing is itself information |
| Page reads as a toy | The inspector copy carries the credibility. Write the `detail` fields as engineering rationale, not feature descriptions |
